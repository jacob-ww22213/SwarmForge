# 集群小模型任务逻辑与专家训练思路

## 1. 这个产品的核心逻辑

SwarmForge 不是把很多小模型简单堆在一起，而是把它们组织成一个有分工的系统。

最核心的思想有 3 个：

1. 单个小模型能力有限，但如果任务可以拆分，就可以让不同节点分别处理不同部分。
2. 系统真正的价值不在“总参数相加”，而在“是否能把任务分配给合适的节点”。
3. 多个小模型最适合做“可拆分、可并行、可交叉验证”的任务，而不是硬扛所有通用聊天问答。

所以这个产品更像：

- 一个分布式专家网络
- 一个任务调度系统
- 一个多节点协作执行平台

而不是一个单体大模型替代品。

## 2. 集群后的小模型适合做什么任务

### 2.1 最适合的任务类型

最适合的任务通常有这几个特征：

- 可以拆成几个子问题
- 每个子问题都不需要超强通用智能
- 不同节点可以从不同视角审查
- 最终结果适合做聚合

典型任务包括：

1. 多视角审查类

- 代码评审
- PR 风险检查
- 架构方案评审
- 文档一致性检查
- 合同或规则风险初筛

2. 可拆解的流程任务

- 把需求拆成开发任务
- 把长文档拆成摘要、行动项、风险点
- 把调研任务拆成多个子问题
- 把会议纪要拆成结论、待办、争议点

3. 批量重复但有轻微差异的任务

- 批量审核商品描述
- 批量分类客服工单
- 批量分析简历
- 批量提取表单字段

4. 需要交叉验证的任务

- 一个节点先回答
- 一个节点挑错
- 一个节点做二次压缩
- 最后一个聚合节点出最终稿

### 2.2 不太适合的任务类型

当前阶段不太适合直接交给集群小模型的任务：

- 非常简单的一句话事实问答
  例如“你是谁”“你是什么模型”
- 高度开放式创作
  例如高质量长篇写作
- 强抽象长链条推理
  例如高难证明、复杂原创研究
- 特别依赖最新世界知识的开放问答

原因不是小模型完全做不了，而是这类任务里：

- 集群协作收益不明显
- 调度成本和通信成本容易高于收益
- 错误还容易被聚合层放大

## 3. 当前最适合拿来做 demo 的任务

如果要给 SwarmForge 选一个最适合演示的任务，我最推荐：

### 多专家协同代码评审

因为它同时满足几个条件：

- 很容易理解
- 很容易拆角色
- 很容易体现多节点协作价值
- 最终输出也容易检查

建议拆成这些角色：

- 功能正确性检查
- 安全风险检查
- 性能与复杂度检查
- 测试覆盖建议
- 最终聚合与总结

## 4. 为什么需要“专家差异化”

如果所有 worker 都差不多，那集群就只是“一堆相似的小模型同时说话”。

真正的价值来自差异化：

- 有的节点更擅长找 bug
- 有的节点更擅长看安全
- 有的节点更擅长拆任务
- 有的节点更擅长压缩总结

所以“很多小模型协作”能不能成立，关键不只是数量，而是：

- 分工是否清晰
- 路由是否有效
- 每个 worker 是否真的拉开能力差异

## 5. 每个小模型都要单独训练吗

不一定。

最现实的路线不是“一开始就给每个 worker 从零训练一个独立模型”，而是分层演进。

### 5.1 第一层：同一个基础模型，不同角色提示词

最简单的方式：

- 所有节点都用同一个基础小模型
- 通过 `role_key`、`role_name`、system prompt 区分身份

例如：

- `coding_worker`
- `research_worker`
- `risk_worker`
- `summary_worker`

优点：

- 成本低
- 最适合早期 demo
- 上手最快

缺点：

- 差异更多是“角色扮演”
- 不是模型能力本身真正分化

### 5.2 第二层：同一个基座，不同 LoRA / adapter

这是更推荐的专家化路线：

- 同样都基于一个基础模型
- 但每个角色挂不同 LoRA

例如：

- `qwen2.5:0.5b + code_review_lora`
- `qwen2.5:0.5b + risk_audit_lora`
- `qwen2.5:0.5b + summary_lora`

优点：

- 训练成本可控
- 部署相对简单
- 差异会比纯 prompt 明显很多

### 5.3 第三层：不同家族模型天然分工

例如：

- 一个偏代码
- 一个偏中文通用
- 一个偏推理
- 一个偏数学

优点：

- 差异天然存在

缺点：

- 调度复杂
- 输出风格更不统一
- 评测更难

### 5.4 第四层：持续训练成会进化的 worker

这是更长期的方向：

- worker 根据任务结果持续积累数据
- 路由命中率更高的节点获得更多该类任务
- 节点根据反馈继续微调

这是“专家网络进化系统”，但不适合最早期 demo 阶段直接做。

## 6. 怎样保证每个 worker 是差异化的

真正的差异化不是改个名字，而是这 4 件事要不同：

1. 训练数据不同

- 代码专家多看代码审查和 bug 分析样本
- 总结专家多看摘要、提炼、压缩样本
- 风险专家多看风险识别、异常案例、合规边界样本

2. 目标任务不同

- 有的节点负责找问题
- 有的负责提方案
- 有的负责二次审查
- 有的负责最后聚合

3. 评价标准不同

- 代码专家看 bug 命中率
- 风险专家看漏报率
- 总结专家看压缩质量
- 聚合专家看最终一致性和可读性

4. 路由入口不同

- 系统必须让不同 worker 接到不同类型的任务
- 不然即使训练了，大家也还是做一样的事

## 7. 怎么让 worker 更好地训练出自己的模型

建议按下面的路线做。

### 第一步：先收数据，不急着训练

先记录这些信息：

- 任务内容
- 被谁路由到
- 输出结果
- 是否被最终聚合采用
- 用户评分
- 延迟
- 错误类型

没有这些数据，后续训练专家就是空谈。

### 第二步：把样本按任务桶整理

例如分成：

- `code_review`
- `task_decomposition`
- `risk_check`
- `doc_summary`
- `final_aggregation`

然后给每个桶积累高质量样本。

### 第三步：先做角色 LoRA，不做重训练

先选 2 到 3 个最值钱的角色做微调：

- `code_review_worker`
- `risk_review_worker`
- `summary_worker`

### 第四步：把反馈回流到路由和训练

记录：

- 哪个 worker 被选中
- 哪个 worker 输出被采用
- 哪个 worker 得分更高
- 哪个 worker 更快

然后用这些数据持续做：

- 路由优化
- 样本再筛选
- 节点再微调

## 8. 代码评审任务的提问模板

下面是一段适合当前系统的提问模板，适合作为代码评审 demo 输入。

### 模板 1：标准代码评审

```text
请对下面这段代码做多专家代码评审。

评审目标：
1. 找出功能性 bug
2. 找出潜在安全问题
3. 找出性能或复杂度问题
4. 给出测试建议
5. 最后输出一个汇总结论

输出要求：
1. 先给一个总体结论
2. 再分成“功能问题 / 安全问题 / 性能问题 / 测试建议”
3. 每个问题尽量说明原因和修复建议
4. 如果没有发现某类问题，也请明确说明

代码如下：

<把代码贴在这里>
```

### 模板 2：带明显错误的代码评审样例

```python
def divide_numbers(items):
    total = 0
    for i in range(len(items) + 1):
        total += 100 / items[i]
    return total


nums = [5, 2, 0]
print(divide_numbers(nums))
```

推荐提问方式：

```text
请对下面这段 Python 代码做代码评审。

请重点检查：
1. 是否存在运行时错误
2. 是否存在边界条件问题
3. 是否存在可读性或健壮性问题
4. 应该补哪些测试用例

代码如下：

def divide_numbers(items):
    total = 0
    for i in range(len(items) + 1):
        total += 100 / items[i]
    return total


nums = [5, 2, 0]
print(divide_numbers(nums))
```

## 9. 以代码评审为例，MoE 阶段现在有没有做角色分类

有，但要说明白：**现在已经有“路由级角色分类”，还没有“训练级专家分化”。**

### 9.1 当前已经有的部分

当前代码里，MoE 阶段确实已经会按 worker 的角色信息做分类和路由。

核心逻辑在：

- [distributed_common.py](/Users/jacob/Documents/cursor/0.5b%20模型的畅想/swarmos_demo/distributed_common.py)

当前通过 `role_key`、`role_name`、`worker_id`、`name` 去推断模板专家类型：

- `coding_engineer`
- `research_scientist`
- `systems_architect`
- `product_strategist`
- `math_optimizer`
- `legal_risk`
- `medical_safety`
- 默认回退 `planner`

具体入口函数是：

- `resolve_template_expert_key(worker)`
- `route_workers(task, workers, phase, top_k, ...)`

### 9.2 当前评分逻辑是什么

现在的 MoE 路由会综合这些因素：

- worker 的角色标签
- 任务解析出来的 `domain`
- 任务动作类型 `action`
- 当前阶段是 `proposal` 还是 `review`
- 任务关键词和 worker 关键词的重合度
- demo / high-risk 之类的附加加权

所以从“工程路由”的角度说，角色分类逻辑已经有了。

### 9.3 当前还没有的部分

现在还没有做到的是：

- 每个角色有真正独立训练过的模型
- 每个角色有自己的 LoRA
- 路由策略根据历史效果持续学习

也就是说，当前是：

- **MoE 路由层已经在做角色分类**
- **但角色差异主要还是靠标签和提示词，不是靠真正的训练差异**

## 10. 当前最现实的下一步

如果要让这个系统更像真正的“专家集群”，最现实的顺序是：

1. 先把代码评审做成标准样板任务
2. 固定 3 个角色
   - `coding_worker`
   - `risk_worker`
   - `summary_worker`
3. 先用同一个基础模型跑通
4. 再给其中 1 到 2 个角色做 LoRA
5. 最后再优化路由学习和专家反馈闭环

一句话总结：

当前系统已经有“MoE 路由级专家分类”，但还没有“训练级专家网络”；最适合先从代码评审这类可拆解、多视角、可验证的任务开始，把专家分工和训练闭环逐步做出来。
