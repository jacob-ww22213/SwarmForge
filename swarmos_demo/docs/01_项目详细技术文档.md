# SwarmOS Demo 项目详细技术文档

## 1. 项目目标

本项目要做的不是一个完整的“10 万专家系统”，而是一个**可运行的 demo 原型**，用来验证下面这条最关键的系统链路：

`任务输入 -> 路由 -> 多专家提案 -> 批判 -> 聚合 -> trace 保存 -> 最终输出`

当前阶段的目标有 4 个：

1. 让系统在本地默认离线可跑
2. 让用户可以直观看到“专家协作”而不是单模型直出
3. 让结果可保存、可回放、可对比
4. 为后续接入真实模型 provider 预留标准接口

## 2. 当前原型状态

当前 workspace 已有一个最小原型：

- 主程序：`swarmos_demo/swarmos_demo.py`
- 示例输入：`swarmos_demo/examples/task_01.txt`
- 示例输出：
  - `swarmos_demo/outputs/task_01.md`
  - `swarmos_demo/outputs/task_01.json`

当前原型已经支持：

- `mock` 离线 provider
- `openai-compatible` provider 预留
- `ollama` provider 预留
- 路由
- 专家提案
- 批判
- 聚合
- markdown / JSON 输出

当前原型的主要局限：

- 所有逻辑仍在单文件中
- 路由还是规则驱动，较像关键词匹配
- 专家行为是 mock 策略，不是真实专精模型
- 缺少基线对比模块
- 缺少独立评测脚本

## 3. Demo 范围定义

### 3.1 本期做什么

本期 demo 聚焦以下能力：

1. 输入一个任务描述
2. 路由到 3 到 5 个专家
3. 专家分别给出提案
4. 批判器指出缺失点和冲突点
5. 聚合器输出最终方案
6. 保存结构化 trace 供后续评测

### 3.2 本期不做什么

本期不做以下内容：

1. 不训练真实 0.5B 专家模型
2. 不做复杂多轮 agent 对话协议
3. 不做分布式多节点部署
4. 不做完整前端 UI
5. 不证明“全面超过大模型”

## 4. 技术架构

建议把 demo 架构拆成 6 层：

1. **CLI / Entry**
2. **Workflow Orchestrator**
3. **Router**
4. **Expert Engine**
5. **Critic + Aggregator**
6. **Reporting + Trace Store**

### 4.1 逻辑流程图

```text
用户输入任务
-> 任务标准化
-> 路由评分
-> 选出 top-k 专家
-> 并行生成专家提案
-> 批判器 review
-> 聚合器整合
-> 输出 console 报告
-> 保存 markdown 报告
-> 保存 JSON trace
```

## 5. 核心模块设计

### 5.1 Task Parser

职责：

- 清洗输入文本
- 判断语言
- 识别任务领域
- 识别动作类型
- 给出风险级别

当前实现方式：

- 简单规则匹配

后续可演进方向：

- 小模型分类器
- embedding 检索式任务识别
- 任务模板归类

### 5.2 Router

职责：

- 为每个专家计算相关性分数
- 选择 planner + top-k specialists
- 输出路由结果和分数

当前实现方式：

- 基于关键词、领域标签和 bias 的规则打分

后续可演进方向：

- 学习式路由
- 历史任务回放调优
- 专家信誉分
- 成本预算约束

### 5.3 Expert Engine

职责：

- 调用被选中的专家
- 生成结构化提案

当前实现方式：

- `MockProvider.propose()`

后续可演进方向：

- 真实模型调用
- 专家专属 prompt 模板
- 不同专家不同 temperature / token 策略

### 5.4 Critic

职责：

- 指出方案缺失项
- 找重复点
- 给出下一步检查建议

当前实现方式：

- 规则式批判

后续可演进方向：

- 独立 critique 模型
- 一致性/冲突检测
- 高风险场景校验模板

### 5.5 Aggregator

职责：

- 汇总共识
- 产出最终摘要
- 给出下一步计划和主要风险

当前实现方式：

- 规则式聚合

后续可演进方向：

- 模型聚合
- 基于专家信誉的加权合成
- 置信度分层输出

### 5.6 Reporting + Trace Store

职责：

- 控制台输出
- markdown 报告输出
- JSON trace 输出

trace 保存的意义：

- 做路由回放
- 做 demo 对比
- 做失败案例分析
- 为后续评测与学习式路由提供数据基础

## 7. Provider 设计

当前建议保留 3 类 provider：

### 7.1 MockProvider

用途：

- 本地默认可跑
- 用于验证流程与结构

优点：

- 无网络依赖
- 易调试
- 输出稳定

缺点：

- 智能性有限
- 容易看起来像规则系统

### 7.2 OpenAI-Compatible Provider

用途：

- 对接任意兼容 OpenAI API 的服务

要求：

- `POST /chat/completions`
- 支持 `model`
- 支持 `messages`

### 7.3 Ollama Provider

用途：

- 本地模型实验

适合用途：

- 快速验证“真实模型 + 协作框架”的效果

## 8. 当前阶段推荐技术栈

为了先跑通，不要把栈做重，推荐：

- 语言：Python 3.12
- 依赖：尽量标准库
- 并发：`ThreadPoolExecutor`
- I/O：本地文件
- 输出：console + markdown + JSON

暂时不需要引入：

- 数据库
- Web 框架
- 消息队列
- 容器编排
- 前端框架

## 9. Demo 验收标准

第一版 demo 的验收标准建议如下：

### 功能验收

1. 能用一条命令跑起来
2. 能读取 inline task 或 task file
3. 能展示路由结果
4. 能输出至少 3 个专家提案
5. 能给出批判和聚合结果
6. 能保存 markdown 和 JSON

### 结构验收

1. provider 是可替换的
2. 专家定义是可扩展的
3. 输出结构是稳定的
4. trace 能被后续脚本读取

### 展示验收

1. 非技术同事也能看懂输出
2. 能看出每个专家的角色差异
3. 能看出“协作”而不是单模型回答

## 11. 最重要的技术原则

1. 先证明流程价值，再追求模型复杂度
2. 先把 trace 做好，再谈评测
3. 先定义标准接口，再并行开发
4. 先做强演示场景，再扩到更多任务

## 12. 结论

这个 demo 的真正价值，不是把“10 万专家”立刻做出来，而是做出一个**可信的系统雏形**：

- 能跑
- 能解释
- 能保存
- 能扩展

只要这个雏形成立，后面无论换 provider、加专家、做评测还是接前端，都有稳定基础。
