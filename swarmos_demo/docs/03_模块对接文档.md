# SwarmOS Demo 模块对接文档

## 1. 对接目标

这份文档只解决一件事：

**让两个人在不互相等待的情况下，围绕固定接口并行开发。**

因此本文件重点不是解释愿景，而是明确：

- 模块边界
- 输入输出字段
- 调用顺序
- 联调约束

## 2. 模块边界

### 模块 A：核心引擎

负责：

- 任务接收
- task profile 生成
- 路由
- workflow 调度
- provider 调用
- trace 保存

输入：

- 原始 task
- CLI 参数

输出：

- routed experts
- workflow trace
- 调用 B 模块所需上下文

### 模块 B：专家与展示层

负责：

- 专家注册表
- proposal 生成
- critic 报告
- aggregate 结果
- console / markdown 报告

输入：

- task
- routed experts
- task profile
- score map

输出：

- expert proposals
- critique report
- aggregate result
- formatted report text

## 3. 共享数据结构

建议统一放在：

```text
swarmos_demo/core/types.py
```

### 3.1 TaskRequest

```python
@dataclass
class TaskRequest:
    task: str
    provider: str
    top_k: int
    save_markdown: str | None = None
    save_json: str | None = None
```

### 3.2 TaskProfile

```python
@dataclass
class TaskProfile:
    language: str
    domains: list[str]
    actions: list[str]
    risk_level: str
    mentions_demo: bool
```

### 3.3 ExpertProfile

```python
@dataclass
class ExpertProfile:
    key: str
    name: str
    role: str
    keywords: tuple[str, ...]
    bias: float = 0.0
```

### 3.4 RoutedExpert

```python
@dataclass
class RoutedExpert:
    key: str
    name: str
    score: float
```

### 3.5 ExpertProposal

```python
@dataclass
class ExpertProposal:
    expert_key: str
    expert_name: str
    role: str
    score: float
    summary: str
    recommendations: list[str]
    risks: list[str]
    confidence: float
```

### 3.6 CritiqueReport

```python
@dataclass
class CritiqueReport:
    focus: list[str]
    duplicates: list[str]
    next_checks: list[str]
```

### 3.7 AggregateResult

```python
@dataclass
class AggregateResult:
    selected_experts: list[str]
    consensus: list[str]
    critique_focus: list[str]
    next_steps: list[str]
    key_risks: list[str]
    final_summary: str
```

### 3.8 WorkflowTrace

```python
@dataclass
class WorkflowTrace:
    task: str
    provider: str
    profile: TaskProfile
    routed: list[RoutedExpert]
    proposals: list[ExpertProposal]
    critique: CritiqueReport
    aggregate: AggregateResult
```

## 4. 标准调用链

建议标准主链如下：

```python
request -> parse_task -> route_experts -> propose_all
-> critique -> aggregate -> render -> save
```

对应职责归属：

### A 模块负责

```python
parse_task(request.task) -> TaskProfile
route_experts(task, profile, top_k) -> list[RoutedExpert], score_map
save_trace(trace)
```

### B 模块负责

```python
propose_all(task, routed, context) -> list[ExpertProposal]
critique(task, routed, proposals, context) -> CritiqueReport
aggregate(task, routed, proposals, critique, context) -> AggregateResult
render_console(...)
render_markdown(...)
```

## 5. 函数接口约定

### 5.1 Router 接口

```python
def route_experts(task: str, profile: TaskProfile, top_k: int) -> tuple[list[RoutedExpert], dict[str, float]]:
    ...
```

约束：

- 返回结果必须按分数排序
- planner 是否强制包含，由 Router 内部负责
- `score_map` 必须保留给 B 模块使用

### 5.2 Propose 接口

```python
def propose(
    expert: ExpertProfile,
    task: str,
    context: dict[str, Any],
) -> ExpertProposal:
    ...
```

约束：

- 每个 proposal 都必须包含 `summary`
- `recommendations` 最少 1 项
- `risks` 允许为空，但字段必须存在
- `confidence` 统一用 0 到 1 浮点数

### 5.3 Critique 接口

```python
def critique(
    task: str,
    routed: list[RoutedExpert],
    proposals: list[ExpertProposal],
    context: dict[str, Any],
) -> CritiqueReport:
    ...
```

约束：

- 至少返回 1 条 `focus`
- 结构必须稳定

### 5.4 Aggregate 接口

```python
def aggregate(
    task: str,
    routed: list[RoutedExpert],
    proposals: list[ExpertProposal],
    critique: CritiqueReport,
    context: dict[str, Any],
) -> AggregateResult:
    ...
```

约束：

- `final_summary` 必填
- `consensus` 最少 1 项
- `next_steps` 最少 1 项
- `key_risks` 最少 1 项

## 6. Context 约定

为减少接口变更，建议 A 模块传给 B 模块的 `context` 固定为：

```python
context = {
  "profile": profile,
  "scores": score_map
}
```

扩展原则：

- 可以新增 key
- 不要轻易改已有 key 名

## 7. Provider 对接约定

### A 模块提供统一 provider 层

provider 对 B 模块透明。  
也就是说，B 模块只关心拿到结构化结果，不应该关心当前底层是 mock、openai-compatible 还是 ollama。

建议 provider 标准能力：

```python
class BaseProvider:
    def propose(...) -> ExpertProposal: ...
    def critique(...) -> CritiqueReport: ...
    def aggregate(...) -> AggregateResult: ...
```

说明：

- 如果是 mock provider，可由 B 模块主导内容策略
- 如果是真实 provider，A 模块负责网络调用，B 模块负责 prompt / parse 规范

## 8. JSON trace 对接约定

trace 输出建议字段固定如下：

```json
{
  "task": "...",
  "provider": "mock",
  "profile": {
    "language": "zh",
    "domains": ["systems", "research"],
    "actions": ["design", "evaluate"],
    "risk_level": "low",
    "mentions_demo": true
  },
  "routed": [
    {
      "key": "planner",
      "name": "Planner",
      "score": 0.63
    }
  ],
  "proposals": [],
  "critique": {
    "focus": [],
    "duplicates": [],
    "next_checks": []
  },
  "aggregate": {
    "selected_experts": [],
    "consensus": [],
    "critique_focus": [],
    "next_steps": [],
    "key_risks": [],
    "final_summary": ""
  }
}
```

约束：

- 字段命名尽量不变
- 可以加字段，但尽量不删字段

## 9. 联调规则

### 规则 1：先定 types，再开工

没有 `types.py` 之前，不建议两个人正式并行改代码。

### 规则 2：A 不直接写 B 的输出内容

A 负责跑通流程，不负责决定每个专家说什么。

### 规则 3：B 不直接改 workflow 执行顺序

B 负责内容模块，不直接控制 orchestrator。

### 规则 4：修改共享结构前必须同步

尤其是：

- `ExpertProposal`
- `CritiqueReport`
- `AggregateResult`

### 规则 5：所有联调以标准样例任务为准

至少保留 3 个标准样例任务，并固定命令。

## 10. 联调检查清单

### A 模块检查项

1. 参数解析是否稳定
2. provider 切换是否不破坏主流程
3. 路由输出是否结构稳定
4. trace 是否完整

### B 模块检查项

1. expert proposal 是否完整
2. critic 是否真的指出缺失点
3. aggregate 是否能直接阅读
4. markdown 输出是否格式清晰

### 联合检查项

1. 跑同一任务能否稳定输出
2. JSON 是否可解析
3. markdown 是否可阅读
4. 输出是否能体现“协作”

## 11. 版本冻结建议

### 冻结点 2：展示冻结

```bash
  --task-file swarmos_demo/examples/task_01.txt \
  --save-markdown swarmos_demo/outputs/task_01.md \
  --save-json swarmos_demo/outputs/task_01.json
```

## 13. 最终目标

这份对接文档的目标不是让两个人“谁都能改所有地方”，而是让两个人：

- 各自有清晰 ownership
- 共享稳定 contract
- 联调时知道该查哪里

只要这三点成立，demo 开发速度会快很多，后面接真实模型和前端也会顺很多。
