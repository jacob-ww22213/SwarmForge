# SwarmOS Demo 双人开发任务拆解文档

## 1. 拆解原则

为了让两个人可以并行开发，同时减少冲突，任务拆解必须满足三点：

1. 文件边界清晰
2. 接口边界清晰
3. 联调顺序清晰

最适合当前 demo 的拆分方式不是“前端 / 后端”，而是：

- **A 线：核心引擎与运行链路**
- **B 线：专家策略与输出展示**

这样拆的原因是：

- 当前项目还没有正式前端
- 最大价值在于系统链路是否跑通
- 两条线可以围绕共享数据结构联调

## 2. 人员分工建议

### 同事 A：核心引擎负责人

负责内容：

- CLI 入口
- task parser
- router
- workflow orchestrator
- provider 抽象
- trace 存储
- 异常处理
- 命令行运行体验

目标：

- 保证 demo 一条命令能跑通
- 保证 provider 后续可替换
- 保证输出结构稳定

### 同事 B：专家与展示负责人

负责内容：

- expert registry
- expert strategy
- critic
- aggregator
- markdown/console report
- 示例任务集
- demo 展示口径

目标：

- 保证专家输出“看得懂、有差异、像协作”
- 保证最终报告适合展示
- 保证输出内容能支持后续评测

## 3. 推荐目录 ownership

### A 线 ownership

建议 A 线负责以下目录：

```text
swarmos_demo/cli.py
swarmos_demo/core/
swarmos_demo/providers/
```

### B 线 ownership

建议 B 线负责以下目录：

```text
swarmos_demo/experts/
swarmos_demo/reporting/
swarmos_demo/examples/
swarmos_demo/docs/
```

### 共享目录

```text
swarmos_demo/outputs/
```

说明：

- `outputs/` 不应手工维护逻辑代码
- 这里只存运行结果和样例输出

## 4. 第一阶段任务拆解

### 阶段 0：无行为变化的重构

这是正式并行开发前必须先做的一步。

目标：

- 把 `swarmos_demo/swarmos_demo.py` 拆成多模块
- 保证拆分前后命令和输出兼容

#### A 线任务

1. 提取 `parse_args()`
2. 提取 `run_demo()`
3. 提取 `analyze_task()`
4. 提取 `route_experts()`
5. 提取 provider 相关类
6. 把 trace 保存逻辑独立出来

#### B 线任务

1. 提取专家定义 `EXPERTS`
2. 提取 `MockProvider` 中的专家提案策略
3. 提取 critic 逻辑
4. 提取 aggregator 逻辑
5. 提取 console / markdown 报告渲染

阶段 0 验收：

- 原命令仍然能运行
- 输出 JSON 字段不变
- 输出 markdown 结构不明显变化

## 5. 第二阶段任务拆解

### A 线：核心引擎工作项

#### A1. CLI 与配置

- 支持 `--task`
- 支持 `--task-file`
- 支持 `--provider`
- 支持 `--top-k`
- 支持保存 markdown / JSON

交付标准：

- 参数错误提示清晰
- 缺失参数时不崩溃

#### A2. Router 模块化

- 提供独立 `Router` 类或函数模块
- 输出专家分数表
- 支持 future：替换成学习式路由

交付标准：

- 输入 task profile
- 输出排序后的 routed experts

#### A3. Workflow Orchestrator

- 统一组织 route -> propose -> critique -> aggregate
- 控制执行顺序
- 捕获 provider 异常

交付标准：

- 外部只调用一个主入口即可完成整个流程

#### A4. Provider 层

- 抽象 `BaseProvider`
- 实现 `MockProvider` 接口兼容层
- 实现 openai-compatible provider
- 实现 ollama provider

交付标准：

- 不同 provider 切换时，不影响 workflow 接口

#### A5. Trace Store

- 保存 JSON trace
- 未来可加 run id / timestamp

交付标准：

- 结构稳定
- 可被评测脚本读取

### B 线：专家与展示工作项

#### B1. Expert Registry

- 专家列表从主流程中抽离
- 每个专家有明确 role、keywords、bias

交付标准：

- 新增专家时不需要改 workflow

#### B2. Expert Strategy

- 把不同专家的 summary / recommendations / risks 生成逻辑拆开
- 避免所有专家写出同一种话术

交付标准：

- 输出具有明显角色差异

#### B3. Critic 模块

- 独立生成关注点、重复点和下一步检查项

交付标准：

- 批判内容不能只是重复最终摘要

#### B4. Aggregator 模块

- 汇总共识
- 输出 final summary
- 生成 next steps / key risks

交付标准：

- 汇总内容应能直接给外部人看

#### B5. Reporting

- console 输出结构优化
- markdown 报告结构优化
- 后续可加 HTML 输出

交付标准：

- 报告适合发给技术合伙人或投资人快速阅读

#### B6. Example Tasks

- 至少准备 3 个任务样例
- 每个样例说明适合展示什么

交付标准：

- 输入足够典型
- 运行输出有明显差异

## 6. 联调顺序

建议按下面顺序联调：

### 第 1 步：先冻结共享数据结构

必须先冻结：

- `TaskProfile`
- `RoutedExpert`
- `ExpertProposal`
- `CritiqueReport`
- `AggregateResult`
- `WorkflowTrace`

如果这一层不先定，后面两条线会频繁冲突。

### 第 2 步：A 线给出 workflow 空骨架

要求：

- 即使 B 线策略还没完成，也能跑占位逻辑

### 第 3 步：B 线按接口回填专家模块

要求：

- 不直接修改 A 线 orchestration 逻辑

### 第 4 步：联合跑样例任务

至少跑：

1. MVP 规划任务
2. 代码审查任务
3. 风险评估任务

### 第 5 步：冻结 V1 demo 输出格式

冻结后：

- 再新增功能时尽量不破坏 JSON 结构

## 7. 每人每日输出建议

### A 线每日输出

- 今日代码改动
- 影响哪些接口
- 是否需要 B 线同步修改
- 当前阻塞点

### B 线每日输出

- 今日新增或修改了哪些专家逻辑
- 输出结构是否变化
- 是否影响 aggregator / report
- 当前阻塞点

## 8. 合并策略建议

1. 每个人尽量只改自己 ownership 范围
2. 共享类型文件改动前先同步
3. 合并前统一跑 3 个样例任务
4. 保留一个稳定命令作为 smoke test

推荐 smoke test：

```bash
python3 swarmos_demo/swarmos_demo.py \
  --task-file swarmos_demo/examples/task_01.txt \
  --save-markdown swarmos_demo/outputs/task_01.md \
  --save-json swarmos_demo/outputs/task_01.json
```

## 9. 时间安排建议

### 第 1 天

- 冻结接口
- 拆分目录
- 完成 ownership 划分

### 第 2 到 3 天

- A 线完成 workflow 骨架
- B 线完成 expert / critic / aggregator 拆分

### 第 4 到 5 天

- 第一次联调
- 修复输出结构不一致

### 第 6 到 7 天

- 补 2 个样例任务
- 优化 markdown 输出
- 做第一次对外演示

## 10. 第一阶段完成定义

双人协作第一阶段完成，至少要满足：

1. 目录结构已拆分
2. 双方能独立开发
3. 一条命令稳定跑通
4. 输出内容可展示
5. 结果可保存、可回放

## 11. 最关键提醒

当前最容易失败的点不是“代码不会写”，而是：

- 接口没有先冻结
- 双方同时改 orchestration
- 输出结构一直变化
- 没有标准样例任务做联调

所以这次协作最重要的是：

**先把对接协议定死，再让两个人同时提速。**
